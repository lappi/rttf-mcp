# rttf-mcp — дизайн

Дата: 2026-09-24
Статус: утверждён к планированию
Предшественник: [ttw-mcp](https://github.com/lappi/ttw-mcp)

## 1. Что это и зачем

MCP-сервер к рейтингу настольного тенниса [rttf.ru](https://rttf.ru) —
второй крупной любительской системе рядом с TTW. Потребитель не человек,
а языковая модель: она получает JSON и делает по нему выводы.

Сервер — прослойка получения данных. Он не считает аналитику, не хранит
состояние и не кэширует, всю интерпретацию делает модель. Это то же
устройство, что у ttw-mcp, и по той же причине: любая арифметика на
стороне сервера — это ошибка, которую модель не сможет заметить.

Объём — **всё богатство RTTF**, включая то, чего у TTW нет вовсе: парный
разряд, отдельная категория нерабочей руки, длительность матчей, залы,
инвентарь.

## 2. Главное ограничение: сайт закрыл именно наши данные

`robots.txt` на `rttf.ru` и `m.rttf.ru` — не общая заглушка, а поимённый
список. Владелец перечислял, что именно нельзя, и в список попало:

```
Disallow: /games      матчи
Disallow: /results    результаты
Disallow: /rivals     очные встречи
Disallow: /ratings    рейтинги
Disallow: /comments
Disallow: /*?*name=*        поиск по имени
Disallow: /*?*date_from=*   фильтр по датам
Disallow: /*?*date_to=*
Disallow: /search
Disallow: /?ajax*
Disallow: /*?*sort=*  /*?*order=*  /*?*title=*  /*?*metro=*
```

Разрешены: `/players/`, `/players/<id>`, `/tournaments/`,
`/tournaments/<id>`, `/halls/`, `/statistics/`, `/topics/`, `/content/`.
Есть `Sitemap: https://rttf.ru/sitemap.xml`.

Сравнение с TTW принципиально. У `r.ttw.ru` стоит `Disallow: /` —
глухая стена без выбора, и ttw-mcp обходит её вежливостью:
последовательные запросы, паузы, честный User-Agent со ссылкой на
репозиторий. У RTTF стена **выборочная**, и выбор сделан осознанно
ровно по тем разделам, которые нам нужнее всего.

К этому добавляется второй факт. На форуме RTTF есть ветка
[«API. Загрузка данных с rttf.»](https://rttf.ru/topics/12192) — прямой
запрос владельца клуба на программный доступ. Ответ администратора:

> «Пока нет и в ближайшее время не планируется. В будущем — возможно.»

Это не принципиальный отказ, а отсутствие ресурсов. Прецедент с
программой TTWR у соседнего TTW показывает, что администраторы работают
с разработчиками напрямую, по почте, просто без документированного API.

### Решение: полный объём за флагом, выключенным по умолчанию

Сервер умеет всё, но по умолчанию отдаёт только разрешённое. Это даёт
две вещи сразу: чистую совесть при выключенном флаге и **предметный
разговор с администраторами** — можно показать работающий инструмент
целиком и спросить разрешения на конкретные разделы, а не просить
абстрактный «доступ к API».

## 3. Где проходит черта

Запреты записаны по URL, но честная граница проходит по **категории
данных**, а не по тому, с какой страницы их удалось получить. Иначе
выходит казуистика: «матчи я брал не с `/games`, а со страницы профиля,
значит можно».

**Правило.** Сервер **всегда читает только разрешённые URL**, в обоих
режимах. Флаг управляет тем, извлекаем ли мы категории, которые сайт
пометил закрытыми, даже когда они попались на разрешённой странице.

Черта ложится по гранулярности, и это согласуется с самим списком:
`/tournaments/` открыт, `/games` и `/rivals` закрыты.

| уровень | открыто | закрыто |
| --- | --- | --- |
| турнир и выше | метаданные турнира, итоговая таблица, участие игрока с местом и балансом | — |
| матч | — | отдельные матчи, счёт, длительность, очные встречи |
| поиск | по городу, типу, наличию результатов | по имени |

### Флаг

Переменная окружения `RTTF_MCP_ALLOW_RESTRICTED`, по умолчанию не
установлена. **Не параметр инструмента**: это решение уровня
развёртывания, а не отдельного вызова, и модель не должна иметь
возможности его переключить.

При выключенном флаге закрытые инструменты **не появляются** в списке
инструментов. Инструмент, который всегда отказывает, — это потраченные
попытки модели и занятое место в её контексте.

Но молчать нельзя. Докстринг `get_player` прямо говорит: данные уровня
матча в этом режиме недоступны, это **не поломка и не отсутствие данных
на сайте**, а сознательное ограничение, включаемое флагом. Без этой
фразы модель решит, что у игрока просто нет матчей, — ровно та
правдоподобная ложь, против которой строится весь проект.

## 4. Инструменты

### Доступны всегда

| Инструмент | Что возвращает |
| --- | --- |
| `get_player(player_id)` | три категории рейтинга (основная, нерабочая рука, пара), максимум рейтинга с датой, сводка, залы, инвентарь, список турниров с местом и балансом |
| `get_tournament(tournament_id)` | метаданные и итоговая таблица |
| `search_tournaments(city, type, with_results, page)` | по разрешённым фильтрам; **без диапазона дат** — он запрещён |
| `list_players(city, page)` | листание разрешённого списка — единственный способ выйти на игрока без поиска по имени |
| `get_hall(hall_id)` | зал; состав полей — предмет замера |

Сигнатуры с `page` условны: **способ листания на RTTF не проверен**.
Страница списка отдаёт сотню строк, явных ссылок пагинации в разметке не
видно — возможен и параметр запроса, и подгрузка. Выяснить до
реализации (раздел 6); от ответа зависит, останется ли `page` числом,
станет ли курсором или исчезнет.

### Только при поднятом флаге

| Инструмент | Основание запрета |
| --- | --- |
| `search_players(name)` | `Disallow: /*?*name=*` |
| `get_player_matches(player_id, …)` | `Disallow: /games`, `/results` |
| `get_head_to_head(player_id, opponent_id)` | `Disallow: /rivals` |

При выключенном флаге игрок задаётся числовым идентификатором, который
берут из адресной строки сайта. Менее удобно, зато честно.

## 5. Архитектура

Отдельный репозиторий. Общими остаются принципы и около двухсот сорока
строк инфраструктуры, **скопированных осознанно**, а не подключённых
библиотекой.

Почему не общая библиотека: двести сорок строк дешевле скопировать, чем
связать — библиотека требует версионирования, релизов и согласованной
починки в двух местах ради объёма в один экран. ttw-mcp опубликован и
работает; превращать его в потребителя библиотеки значит ломающе
переделать рабочую вещь без выгоды для пользователя. А главное — сайты
расходятся сильнее, чем кажется (раздел 6), и общая абстракция на двух
точках данных зафиксировала бы в интерфейсе случайное совпадение.

Если появится третий сервер — тогда извлекать, уже зная, что общее на
самом деле.

```
rttf_mcp/
  client.py      сеть; копия ttw-mcp с правкой базового URL и пауз
  errors.py      RttfError → NotFound / ParseError / UpstreamError / InvalidInput
  policy.py      НОВОЕ: флаг, перечень закрытых категорий, регистрация инструментов
  collect.py     последовательный сбор нескольких страниц, копия
  parsers/
    common.py    хелперы: clean, parse_date, parse_number, require, text_of
    player.py
    tournament.py
    halls.py
  server.py      инструменты и контракты для модели
```

**Не переносится:**

- `reconcile.py` — он сводил матчи турнира из профилей участников, потому
  что у TTW страница турнира матчей не содержит. У RTTF матчи лежат в
  профиле напрямую, а `/games` закрыт: сводить нечего и незачем.
- `rating.py` в прежнем виде — там восстанавливали рейтинг на дату
  вычитанием дельт по недельным периодам. RTTF показывает максимум
  рейтинга с датой и дельту у каждого матча; арифметика другая, и какая
  именно — предмет замера, а не переноса.

**`policy.py` отдельным модулем**, а не парой условий в `server.py`:
решение «что мы вообще готовы отдавать» самостоятельно, его надо читать
в одном месте и покрывать тестами без сети.

## 6. Чем данные RTTF отличаются от TTW

| | TTW | RTTF | Последствие |
| --- | --- | --- | --- |
| Идентификатор | шестнадцатеричный | числовой | другая валидация: `[0-9]+` и `fullmatch` |
| Рейтинг | два знака | целый | **природа округления — предмет замера** |
| Нерабочая рука | отдельный профиль с отдельным id | категория внутри профиля | `split_hand` не нужен; зато три рейтинга в одном ответе |
| Парный разряд | нет | есть | у матча четыре участника, а не два |
| Длительность матча | нет | есть, в минутах | новое поле |
| Залы, инвентарь | нет | есть | новые сущности |
| Списки | без пагинации, потолок 500 | способ листания не выяснен | нужен честный признак «есть ещё» |
| Города | нет | `cities[]`, коды вида `r77` | фильтр-массив в query |
| Домены | один | `rttf.ru` и `m.rttf.ru` | выбрать один; списки запретов почти идентичны |

Известная разметка (из чужого парсера, см. раздел 9): список игроков —
`section.players-list tr`, ячейки «место, имя со ссылкой, город, рейтинг
в `dfn`»; профиль — `/players/<числовой id>`; турнир —
`/tournaments/<числовой id>`.

### Замерить до реализации, а не предполагать

1. **Природа округления рейтинга.** Целое число может быть усечением или
   округлением внутреннего дробного значения. Нужен **различающий**
   случай — профиль, где дробная часть больше половины. См. раздел 7.
2. **Смысл рейтинга соперника в строке матча.** Исторический на момент
   встречи или сегодняшний? У TTW это оказалось **по-разному в разных
   блоках одной страницы**: в списке матчей исторический с двумя знаками,
   в блоке лучших побед — тот же исторический, но округлённый, а рядом
   собственный рейтинг игрока был вообще сегодняшним. Проверять каждый
   блок отдельно.
3. **Время ответа сайта.** От него зависит политика пауз и то, какие
   многозапросные инструменты вообще осмысленны.
4. **Есть ли внешняя опора для проверки расчётов.** См. раздел 7.
5. **Полнота списков.** Усечены ли матчи и турниры в профиле, есть ли
   потолок, отличается ли он от заявленного счётчика.
6. **Способ листания.** Страница списка игроков отдаёт сотню строк, а
   явных ссылок пагинации в разметке не видно. Параметр запроса,
   подгрузка или что-то третье — выяснить; от этого зависит сигнатура
   `list_players` и возможность честно сказать «есть ещё».
7. **Состав страницы зала.** `/halls/<id>` разрешён и присутствует в
   sitemap, но его содержимое не осмотрено. Если там нет ничего сверх
   того, что уже отдают турниры, инструмент `get_hall` из объёма
   выпадает.

## 7. Грабли ttw-mcp, заложенные заранее

Это то, за что уже заплачено в предыдущем проекте.

**Замер по перечню слеп к неперечисленному.** Пометку руки искали
фильтром `левая|правая` и отчитались о «четырнадцати замеренных формах».
Творительный падеж в выборку не попал и потому «не существовал»;
найденный позже, он давал `hand: null` у помеченных игроков — «не
опознал» выдавалось как «пометки нет».

*Правило:* любой замер «какие бывают формы» начинается с широкого прохода
по признаку и подсчёта, **сколько объектов не попало ни в одну форму**.
Сужение — только после.

**Пример ценен тем, что мог бы опровергнуть.** Значение объявили
усечённым по трём примерам, у которых дробная часть была меньше половины,
то есть ни один не различал усечение и округление. Различающий случай
нашёлся сразу и опроверг вывод.

*Правило:* подбирая примеры под утверждение, спрашивать, какой пример его
опроверг бы. Если такого в выборке нет — утверждение не проверено, и это
надо сказать прямо. Для целых рейтингов RTTF это первый пункт замеров.

**Тест, проходящий при удалённой реализации.** Ассерт через `.get()`
возвращает `None` и когда ключа нет вовсе, из-за чего целая ветка кода
оказалась непокрытой.

*Правило:* доступ к проверяемым полям только индексацией.

**Тавтология в тестах.** Ожидание, вычисленное тем же выражением, что и
реализация, проходит, даже если оба неверны. Спасла внешняя опора: сайт
сам публиковал рейтинг соперника до турнира, и расчёт совпал с ним
восемь раз из восьми.

*Правило:* для любой восстановленной величины искать независимый источник
на самом сайте. Для RTTF наличие такой опоры — предмет замера, и если её
нет, это надо записать как известное ограничение, а не делать вид.

**Потолки, обходимые произведением.** Диапазон дат ограничили
четырнадцатью днями, а обогащение строк прошло мимо потолка: четырнадцать
дней на двадцать строк дали бы до двухсот восьмидесяти запросов.

*Правило:* у каждого многозапросного пути свой потолок, и при композиции
проверяется произведение, а не сомножители.

**Формальная проверка вместо настоящей.** Регулярка формата пропускала
`31.02.2026`, запрос уходил в сеть и возвращал пустоту, неотличимую от
«ничего не нашлось».

*Правило:* всё, что похоже на дату или число, проверяется по существу, до
обращения к сети.

**Ошибка, стёртая на границе.** Исключение не из своей иерархии
превращалось в «Error executing tool» без причины.

*Правило:* декоратор `_reporting` переносится целиком; любое исключение
сторонней библиотеки заворачивается в свой тип.

**Разнородные словари.** Поле, которое то есть, то нет, модель не
отличает от пустого значения.

*Правило:* отсутствие ключа означает «не запрашивали», `null` —
«запрашивали, не вышло». На RTTF это острее: три категории рейтинга, и у
большинства игроков заполнена одна.

**Имя поля, которое врёт.** В таблице турнира TTW поле называлось
`rating`, а содержало сегодняшнее значение, расходящееся с историческим
на сотни пунктов.

*Правило:* если поле содержит сегодняшнее значение, в имени стоит
`_current`; если восстановленное на дату — `_at_event`.

**Докстринг — единственный канал.** Модель не может проверить данные и
узнаёт об особенностях источника только из докстринга. Неполный
докстринг здесь — дефект, а не придирка о стиле; цена вызова в запросах
и все причины `null` называются явно.

## 8. Ошибки, фикстуры, тесты

Иерархия ошибок и подход к тестам переносятся целиком.

- Офлайновые тесты на сохранённых страницах; **фикстуры не в git** — в
  профилях RTTF те же ФИО реальных людей. Восстановление скриптом
  `scripts/fetch_fixtures.py`, последовательно, с паузами.
- ФИО не попадают ни в код, ни в тесты, ни в сообщения коммитов, ни в
  историю. В тестах — слова «Фамилия», «Имя», «Отчество»; игроки
  называются идентификаторами.
- Smoke-тесты против живого сайта под маркером `smoke`, вне обычного
  прогона, запускаются вручную.
- Парсер обязан падать громко на неопознанной разметке: якоря `require()`
  с именем парсера и селектора.

**Новый класс тестов — на `policy.py`:**

- при выключенном флаге закрытые инструменты отсутствуют в списке;
- при поднятом — появляются;
- в выключенном режиме **ни один закрытый URL не запрашивается** —
  проверяется заглушкой-канарейкой, которая роняет тест при обращении.

## 9. Чужие наработки

[`Annovid/rttf-bot`](https://github.com/Annovid/rttf-bot) — телеграм-бот
на Python, живёт с октября 2024-го. Лицензии у репозитория **нет**,
поэтому из него берутся только факты о чужой разметке (они не являются
его собственностью), но **не код**.

Полезные факты: мобильный поддомен `m.rttf.ru`, числовые `/players/<id>`,
селектор `section.players-list tr` и состав ячеек, коды городов вида
`r77`.

Он же — живой антипример по всем трём пунктам, которые в ttw-mcp решены
осознанно иначе:

- базовый парсер ловит **любое** исключение и возвращает `None` —
  поломка разбора неотличима от честной пустоты;
- подделывает User-Agent под Chrome — мы представляемся своим именем со
  ссылкой на репозиторий;
- ходит параллельно через `ThreadPool` — мы строго последовательно.

Первый пункт берётся в тесты как контрольный случай: на мусорной
разметке наш парсер обязан падать громко.

Прочее найденное: [`sgolovan/rttf-player-charts`](https://github.com/sgolovan/rttf-player-charts)
улучшает графики на самом сайте, к получению данных отношения не имеет.
MCP-серверов для настольного тенниса не существует ни одного — проверено
поиском по GitHub.

## 10. Вне объёма

- **Связывание профилей между TTW и RTTF.** Один человек имеет учётные
  записи в обеих системах, но сопоставлять их по имени — значит ошибаться
  на однофамильцах. Отдельная задача с отдельной ценой ошибки.
- **Кэш и любое состояние на диске.** Как и в ttw-mcp: сервер отдаёт
  данные, состояние ведёт модель.
- **Запись.** Только чтение.
- **Обход ограничений сайта.** Никаких попыток достать закрытые разделы
  окольным путём, ни в одном из режимов.
